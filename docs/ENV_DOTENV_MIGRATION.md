# Migration Guide: docker-compose.env → repo-root .env compatibility ✅

**Epic:** Refactoring Docker Environment Variables

This document explains the migration rationale, step-by-step actions, acceptance criteria, and rollback steps for converting the repository to use a repo-root `docker-compose.env` as the authoritative source of truth while generating a compatibility `./.env` file for legacy `docker-compose` (hyphen) clients.

## Summary
- Keep `docker-compose.env` at the repository root as the authoritative environment file.
- Generate a resolved, compatibility `./.env` (repo root) for legacy clients that automatically load `.env` files (Windows `docker-compose`, older clients).
- The generated `.env` must contain resolved values (no unresolved `${...}` patterns), and be ignored by Git.

## Why this change? 💡
- `docker-compose` (modern CLI) supports `--env-file`, which lets us keep `docker-compose.env` as authoritative.
- Some environments or users use legacy `docker-compose` which automatically reads a `.env` file in the compose directory. Generating a compatibility `./.env` avoids accidental misconfiguration and makes local developer experience consistent on Windows.

## Files changed / authoritative sources
- Authoritative: `./docker-compose.env` (repo root)
- Compatibility: `./.env` (repo root) — generated by `scripts/sync_dotenv_from_compose_env.js` (via `npm run env:sync`)
- Validator: `scripts/validate_env_py.py` and `scripts/validate_env.sh` assert required variables and simple value checks.

## Local developer steps 🧭
1. Generate the compatibility `.env`:
   ```bash
   npm run env:sync
   ```
   Optional wrappers (same Node implementation):
   - `bash scripts/sync_dotenv_from_compose_env.sh`
   - `pwsh -NoProfile -File scripts/sync_dotenv_from_compose_env.ps1`
2. Validate the generated `.env`:
   ```bash
   npm run env:validate
   # or: python scripts/validate_env_py.py
   ```
   Expected output (example):
   ```
   OK: required env vars present: INDEX_DIR=/data/indices, MEDIA_DIR=/usr/src/paperless/media, VISUAL_RAG_INDEX_NAME=paperless_visual, VIDEO_FRAME_INTERVAL=1, VIDEO_KEYFRAME_DETECTION=yes
   ```
3. Confirm `.env` contains no unresolved `${...}` patterns:
   ```bash
   grep -n '\${' .env || echo 'No unresolved patterns found'
   ```

## CI expectations
- A `validate-env` job runs on PRs (and pushes to `main`) that:
  - Runs the sync step (POSIX + PowerShell as appropriate)
  - Runs `scripts/validate_env_py.py` (or `npm run env:validate`)
  - Ensures generated `.env` has parity with `docker-compose.env` (variable counts match) and no unresolved `${...}` patterns

The repository contains `.github/workflows/validate-env.yml` that performs these checks for Linux and Windows runners.

## Acceptance Criteria ✅
- [ ] `npm run env:sync` successfully creates a repo-root `./.env` with resolved values.
- [ ] `npm run env:validate` exits with code 0 and prints the OK message above.
- [ ] The generated `.env` contains no `${...}` patterns.
- [ ] `docker-compose.yml` services point to `env_file: .env` (compatibility) and include explicit `environment:` mappings for service-specific variables that must not be empty (e.g., `MEDIA_DIR`, `INDEX_DIR`, `VISUAL_RAG_INDEX_NAME`, `DEFAULT_INDEX_NAME`).
- [ ] The `validate-env` CI job runs on PRs and fails if required envs are missing or invalid.

## Rollback strategy ⚠️
- Changes are non-destructive: `docker-compose.env` remains authoritative.
- If a problem occurs with the generated `.env`, revert the PR and/or remove `./.env` from the working tree. The `docker-compose.env` file remains untouched.

## FAQ / Troubleshooting
- Q: I ran `env:sync` and `.env` still contains a `${...}` pattern. What to do?
  - A: Check for nested expressions that depend on environment variables outside `docker-compose.env`. The generator resolves only variables defined in `docker-compose.env` or defaults in expansions like `${VAR:-default}`. Ensure all referenced variables have defaults or are defined.

- Q: Why do we commit `docker-compose.env` with secrets?
  - A: We recommend moving secrets to Docker secrets or CI secret managers for production. `docker-compose.env` should be minimal for team use; do not commit production secrets if avoidable.

## Notes for maintainers
- Keep the helper scripts in `scripts/` small and well-tested.
- If you alter authoritative variable names, update `scripts/validate_env_py.py` and the CI workflow concurrently to prevent regressions.
